# 05. Блокировка и разблокировка пользователя

Обязательный контекст: [общий контракт](README.md). Один общий диалог с двумя режимами, вызов из списка или карточки. Не создавать отдельные страницы подтверждения.

## Назначение и условия

Администратор временно прекращает доступ обычного пользователя своей лаборатории или возвращает его. Собственная административная учётная запись и другие администраторы исключены. «Заблокировать» доступно для активного пользователя, «Разблокировать» — для заблокированного. Активации и статуса «Ожидает активации» больше нет ([07](07-account-activation.md)). Условия сверяются адаптером при подтверждении.

Правила сеансов/разблокировки — проектное решение из README. Не подменять блокировку снятием всех прав и продукции: назначения остаются сохранёнными.

## Макет

Заголовок «Заблокировать пользователя?» или «Разблокировать пользователя?». Сведения: фамилия/имя, логин, текущий статус. Использовать рабочие информационные поля. Опциональную причину блокировки на этом этапе не добавлять: она требует отдельного правила хранения, а не нужна для подтверждения.

| Режим | Пояснение | Действия |
| --- | --- | --- |
| Блокировка | «Пользователь не сможет работать в системе. Открытые сеансы будут завершены. Несохранённые изменения будут потеряны. Сохранённые документы останутся.» | «Отмена», «Заблокировать» |
| Разблокировка | «Пользователь снова сможет войти. Сохранятся ранее назначенные права и типы продукции.» | «Отмена», «Разблокировать» |

Опасное оформление — только документированный общий вариант рабочей кнопки. Иконки `admin-lock`/`admin-unlock` из общего реестра. Диалог и поведение фокуса — общий контракт; исходный фокус на «Отмена». На узком экране сведения переносятся, кнопки доступны без горизонтальной прокрутки.

## Поведение

1. До подтверждения ничего не менять. Escape, крестик и «Отмена» закрывают диалог без записи истории.
2. При подтверждении — «Блокируем…»/«Разблокируем…», предотвращение повторов. Успех только после ответа, без оптимистического изменения статуса.
3. После блокировки статус обновляется в инициирующей карточке/списке, появляется «Пользователь заблокирован», фиксируется одно событие истории.
4. После разблокировки статус снова «Активен». Права/продукция те же, автоматического входа нет.
5. При ошибке диалог остаётся, объяснение и повтор доступны. Нет ложного сообщения успеха. Если статус изменился в другом окне — обновить сведения: «Состояние пользователя изменилось», не отправлять противоположное действие автоматически.
6. Если запись удалена/недоступна, действие прекращается; после закрытия обновить список либо показать недоступность карточки. Фокус возвращается к инициатору, если он существует.

## Storybook и приёмка

Примеры обоих режимов, отправка, отказ, конфликт статуса, длинные сведения, 390 px. Проверить клавиатуру, Escape и возврат фокуса.

Браузерный сценарий: активный пользователь редактирует ВСЭ в другой вкладке → администратор блокирует его → рабочий доступ прекращён, новые изменения не сохранены → администратор разблокирует → пользователь входит снова с прежними правами. Ранее сохранённая ВСЭ и её авторство остаются.
