## 2. Подтверждённые правила продукта

Источник — решения владельца продукта в текущем обсуждении. Они приоритетнее старых демонстрационных данных.

1. Администратор только управляет пользователями. Рабочие поступления, журнал ВСЭ, справочники и выбор продукции ему не нужны.
2. У обычных пользователей нет ролей. Доступ задаётся пятью независимыми разрешениями и набором типов продукции. Не вводить роли «Врач», «Старший специалист», «Наблюдатель», шаблоны ролей или редактор ролей.
3. Пользователь видит записи своей лаборатории. Права на действие не расширяют границы лаборатории и продукции.
4. Если во время заполнения отозван необходимый доступ, несохранённая запись не сохраняется. Это относится и к изменениям существующей записи: предыдущая сохранённая версия остаётся, новые изменения отбрасываются.
5. Администратор не может изменять собственные права. В этом разделе создаются обычные пользователи; создания администраторов и изменения их статуса не проектировать.
6. Точные подписи разрешений и продукции зафиксированы в ТЗ 04. Они одинаковы в формах, профиле, сводке и истории.

Технический признак административной учётной записи допустим для маршрутизации и проверок, но не является назначаемой ролью обычного пользователя. Поле «Роль» в формах и таблице не добавлять.

## 3. Проектные решения для демонстрации и вопросы перед бэкендом

Ниже — явные предложения этого ТЗ, а не дополнительно подтверждённые владельцем бизнес-правила. Они позволяют реализовать согласованный демонстрационный сценарий. Агент не должен выдавать их за решения владельца или менять молча.

| Вопрос | Конкретное поведение макета | Что согласовать перед бэкендом |
| --- | --- | --- |
| Область администрирования | Обычные пользователи той же лаборатории, что у администратора; лаборатория неизменяема | Бывают ли администраторы нескольких лабораторий |
| Базовое чтение | Вход и просмотр доступны активному пользователю с продукцией без выдачи дополнительных прав; пять флажков управляют только названными действиями | Доступ к сверке, подтверждению, печати, экспорту и повторному осмотру: не добавлять им разрешения самостоятельно |
| Область пяти прав | Один набор прав действует на все назначенные типы продукции | Нужны ли разные наборы для разных типов; в текущих макетах матрицы «право × продукция» нет |
| Нулевой доступ | Можно сохранить пользователя без прав и без продукции; это явно показано, никаких назначений по умолчанию | Допустим ли рабочий вход без продукции |
| Регистрация | Администратор создаёт запись и сам задаёт логин и пароль; пользователь входит по ним. Активация и приглашения по email не предусмотрены | Сдача логина/пароля пользователю, восстановление забытого пароля обычным пользователем, политика паролей |
| Идентификаторы | Логин и email — разные поля; логин не обязан быть email. Логин неизменяем после создания; email служит контактом для связи | Область уникальности логина/email, подтверждение и смена email, возможность менять логин |
| Блокировка | Прерывает рабочий доступ и сеансы; разблокировка возвращает прежние права/продукцию, не даёт новых | Механизм прекращения сеансов и доставки изменений доступа |
| Удаление | Демонстрация допускает удаление только записи без связанных рабочих документов; при связях предлагает блокировку. История изменений сохраняется | Окончательные правила удаления/архивирования, повторное использование логина, хранение истории и персональных данных |

Для политики паролей использовать одну явную демонстрационную конфигурацию demo-адаптера (`VseAuth.demoPasswordPolicy`). Её значения подписать в документации как демонстрационные, не разносить константы по страницам. Не изобретать нормативные требования к паролям или реальные гарантии удаления.

## 5. Защита от визуальных расхождений

- Оставить HTML и обычный JavaScript. Общие новые элементы размещать в `components/`, предметные составные элементы — в `components/admin/`. Не добавлять React/Vue, новый UI-kit или другую дизайн-систему.
- Существующие цвета, Inter, плотность, радиусы, поверхности и фокус брать из действующих токенов и компонентов. Для рабочей формы ориентир — профиль и рабочие экраны, не крупная форма входа. Страница сохраняет естественную прокрутку.
- Не менять общие токены ради одного экрана. Новую необходимую метрику оформить один раз в общем административном слое и описать назначение. Не копировать числовые значения в независимые страницы и stories.
- В шапке сохранить `VseAppHeader.spec`: высоту 76 px, логотип 43 × 43 px, пункты 42 px, навигационные иконки 19 px и остальные действующие интервалы. Эти числа — контрольные ориентиры, не повод повторно прописать CSS на странице. Эталон — общий компонент и его спецификация.
- Административная конфигурация меняет только состав навигации и назначения ссылок. Не расширять кнопки, не уменьшать шрифт всей шапки и не сжимать отступы ради длинного названия раздела. Применять её действующую адаптацию.
- Существующие `arrivals`, `journal-classic`, `directories-classic`, `meat`, `milk` остаются со своими SVG. Запрещено заменять их библиотечными аналогами при добавлении административных возможностей.
- Не вводить декоративные графики, счётчики-плитки, боковое меню, новый бренд, градиенты рабочих кнопок или лишние карточки, если они не решают описанный сценарий.
- Все административные стили ограничить своей областью. Не переопределять локально `.topbar`, `.navlink`, `.app-button`, `.profile-*` и общие селекторы ради подгонки.

## 6. SVG-иконки из готовой библиотеки

Сначала использовать существующий общий реестр по назначению. Для новых отсутствующих знаков использовать SVG из **одной библиотеки Lucide**: [статические SVG](https://lucide.dev/guide/static), [users-round](https://lucide.dev/icons/users-round), [лицензия](https://lucide.dev/license). Библиотека не является основанием заменить уже утверждённые иконки.

Новые SVG добавить один раз в общий реестр `components/icons/`; для нового пункта шапки использовать этот же источник через `AppHeader.createIcon`, без второго набора path. Сохранить источник, выбранную версию/ревизию и требуемые тексты лицензий локально. Существующий реестр шапки не переносить массово ради этой задачи.

| Назначение | Общий смысловой ключ | Источник нового SVG |
| --- | --- | --- |
| Управление пользователями | `admin-users` | Lucide `users-round` |
| Добавить пользователя | `admin-user-add` | Lucide `user-plus` |
| Редактировать | `admin-edit` | Lucide `pencil` |
| Блокировать / разблокировать | `admin-lock` / `admin-unlock` | Lucide `lock-keyhole` / `lock-keyhole-open` |
| Удалить | `admin-delete` | Lucide `trash-2` |
| История | `admin-history` | Lucide `history` |
| Приглашение | `admin-invite` | Lucide `mail` |
| Повторить / очистить / поиск | `admin-retry` / `admin-clear` / `admin-search` | Lucide `rotate-ccw` / `x` / `search` |

Смысловые ключи таблицы — план расширения, сейчас их нет в API. Сначала реализовать реестр и stories, затем вызывать. Запрещены рисование path агентом, эмодзи вместо SVG, пиктограммы шрифтом, вставка одинакового SVG в страницы, CDN-зависимость при открытии с диска. Размер, цвет через `currentColor` и обводку задаёт общий компонент; исходную геометрию SVG не переделывать. Декоративный SVG — `aria-hidden`, доступное имя — у кнопки. Неизвестный ключ выявляется до показа страницы.

Текущий `VseApp.createButton` трактует строковый `icon` как ключ своего `components/app/Icon.js`, где административных ключей пока нет. Для нового SVG допустим поддерживаемый параметр `icon` с готовым DOM-элементом из общего реестра либо документированное расширение общего адаптера. Не передавать `icon: 'admin-edit'` в прежний API и не подменять неизвестный значок случайным существующим.

Для продукции обязательных новых значков не требуется: все шесть пунктов можно показывать текстом. Для существующих мяса/молока не подбирать новые аналоги. Не обозначать будущую продукцию мясом или молоком.

## 7. Общая модель и демонстрационные данные

Единый источник данных для всех макетов, без массивов пользователей внутри каждой страницы. Предлагаемый интерфейс demo-адаптера описать в `components/admin/README.md`; это новая API, её имена не считать уже существующими.

- Пользователь: стабильный `id`, `laboratoryId`, имя, логин, email, должность, пять флагов прав, массив кодов продукции, статус, дата создания, версия записи.
- Статусы учётной записи: «Активен», «Заблокирован». Активации нет: созданная запись сразу активна. Удалённая запись не является активным участником списка.
- Приглашение: отдельные состояние доставки, срок, факт использования/отзыва. Повторная отправка не создаёт нового пользователя. Активация не снимает блокировку.
- История: событие, субъект, исполнитель, дата/время, изменения «было → стало» с русскими подписями, версия. Пароли и токены не записывать.
- Все операции асинхронные через адаптер: чтение, создание, изменение, проверка связей/удаление, блокировка, разблокировка, история, проверка текущего доступа. Ошибки имеют различимые причины, а не одну строку на всё.
- В демонстрации использовать только синтетические данные; email вида `anna.kuznetsova@example.test`. Рабочие записи из существующих макетов не удалять и не подменять.
- Общий demo-store хранить в отдельном пространстве имён, например `vse-admin-demo-v1`, только для фиктивных данных. Предусмотреть переход между HTML-страницами и синхронизацию вкладок; при недоступном storage — сессионный режим с честным сообщением об ограничении. Истории Storybook получают изолированное состояние и сбрасываются при повторном открытии.
- Для сценария отзыва доступа предусмотреть управляющую тестовую фикстуру. Технические переключатели ошибок и текущего пользователя размещать в Controls/тестовой оснастке, не в продуктовом интерфейсе.
- Новые страницы открываются с диска обычными скриптами в порядке зависимостей и через локальный сервер. ESM `story-support.js` — только адаптер каталога, не зависимость HTML-страницы. На HTTP дополнительно проверять межвкладочную синхронизацию; не обещать одинаковую работу `storage` для разных `file://` в любых браузерах.

## 8. Правила взаимодействия для всех макетов

1. Ссылки осуществляют переход, кнопки — действие. Каждая видимая доступная кнопка работает; нет заглушек с молчаливым кликом. Создание/сохранение/удаление имеют ожидание, успех, ошибку и повтор без дублей.
2. Поиск, фильтры, сортировку и страницу списка сохранять на время переходов «список → карточка → список» в сессии, без записи email/поиска в URL. Это продолжает временную модель фильтров проекта. ID пользователя допустим в URL; пароль, токен и текст формы — нет.
3. Формы без автосохранения. При уходе с изменённой формы — общий диалог «Изменения не сохранены» с действиями «Продолжить редактирование» / «Выйти без сохранения». При реальном закрытии вкладки допустим стандартный `beforeunload`. Отзыв доступа имеет приоритет: не предлагать сохранить или экспортировать запрещённые данные.
4. Ошибки полей — рядом с полем, общая ошибка — в форме; введённое сохраняется при сетевой/валидационной ошибке. Фокус на первой ошибке. Блокировка повторной отправки не меняет геометрию кнопки. Для конкурирующих изменений — конфликт версий с предложением загрузить актуальную запись, без молчаливого затирания.
5. Опасные действия — общий `dialog`, стилистически согласованный с существующими подтверждениями; не `alert/confirm/prompt`. Фокус внутри, фон недоступен, исходный фокус на «Отмена». Escape/закрытие отменяют до отправки. Во время операции закрытие не должно создавать ложного впечатления отмены уже отправленного запроса; краткое busy-состояние, затем результат или ограниченная по времени ошибка. После закрытия — возврат к инициатору либо ближайшему логичному элементу, если он удалён.
6. Успех — единообразное сообщение в области страницы с `role=status`, ошибки — доступное уведомление. Готового Toast API сейчас нет: не ссылаться на удалённый `Toast.js` и не выдумывать `VseApp.showToast`. При необходимости повторяющийся компонент обратной связи создать и документировать один раз.
7. Русский язык во всех видимых и доступных подписях. Даты `ДД.ММ.ГГГГ ЧЧ:ММ`, единая зона демонстрации `Europe/Moscow`; в истории явно указать «МСК». Отсутствующее значение — «Не указано», а не случайные пустые поля.
8. На 1440, 1024, 768 и 390 px сохраняются порядок, доступность действий и естественная прокрутка. Шапка использует собственные брейкпоинты. На узком экране формы в одну колонку, длинные названия продукции переносятся полностью. Для списка допускается мобильное представление тех же данных без дублирования логики. Нет горизонтальной прокрутки всей страницы и обрезанных кнопок.
9. Клавиатура: Tab, Shift+Tab, Enter/Space по нативным правилам, Escape для открытых слоёв. Видимый фокус; подписи связаны с полями; ошибки через `aria-describedby`/`aria-invalid`; состояние не передаётся одним цветом. Важные данные доступны без наведения.
10. Отказ в доступе проверяется до отображения данных и при каждой мутации. Клиентская проверка служит демонстрацией, будущий сервер обязан повторять её и применять изменение атомарно. Другую лабораторию не выбирать ни в форме, ни параметром URL.

## 9. Storybook и приёмка реализации

- До нового компонента проверить существующий в каталоге. Расширение общего API описать в README его владельца, добавить stories рядом с исходником. Один runtime используется страницами и каталогом; stories не содержат альтернативной верстки, CSS и бизнес-логики.
- Общую шапку дополнить примерами администратора, ограниченного рабочего доступа и отсутствия продукции. Новый раздел каталога — «Администрирование», встроенные повторяющиеся элементы — отдельные компоненты. Состояния перечислены в каждом ТЗ; для неприменимых состояний не создавать искусственные примеры.
- Минимально проверить обычное, ожидание, ошибку/повтор, недоступность, длинные данные и 390 px; для списков — пусто/нет совпадений, для диалогов — клавиатуру и возвращение фокуса, для форм — изменённость и ошибки.
- После изменения Storybook выполнить `npm.cmd run build-storybook`. При изменении компонентов авторизации — затем `npm.cmd run test:ui`. Существующие проверки `tests/auth.spec.js` и `tests/profile.spec.js` должны продолжать проходить.
- Для нового административного поведения добавить предметные браузерные сценарии: права/продукция, CRUD, блокировка/разблокировка, конфликт и отзыв доступа. Не ограничиваться тестами существования кнопок. Предлагаемый новый файл — `tests/admin.spec.js`; он ещё не существует.
- Проверить реальную HTML-страницу и её компонент в Storybook, включая переходы между страницами. Сборка каталога не подтверждает поведения приложения.
- Сравнить шапку администратора со шапкой рабочего экрана: общий источник, размеры, отступы, профиль и фокус. Сравнить рабочую шапку до/после расширения: SVG и геометрия не изменились. Проверить профиль без старых прав по умолчанию.
- Зафиксировать результаты проверок и снимки широкого/узкого экранов. Проверить отсутствие ошибок консоли, битых ссылок/ресурсов, случайных SVG и обязательных зависимостей от `tmp/`.
- Макет принят, когда сценарии его файла проходят, общие критерии выполнены, демонстрационные допущения отмечены и нет скрытых новых прав/ролей. Изменения посторонних существующих макетов не входят в этот этап.

## 10. Границы этапа

Не разрабатывать бэкенд, реальную рассылку, управление лабораториями/администраторами, новые рабочие экраны четырёх будущих направлений продукции, массовые действия, импорт/экспорт пользователей и полноценный журнал безопасности всей системы. Назначение всех шести типов доступно в админских макетах; отсутствие рабочего маршрута для четырёх типов не должно вести на мясной или молочный экран. Показать честное состояние «Раздел ещё не реализован» в той же оболочке, без фиктивных записей.

Рабочие экраны не дублировать под администратора. В существующих экранах затрагивать только необходимые общие состояния, единый источник доступа, навигацию и данные профиля; все прежние рабочие маршруты и предметные сведения сохранить.
